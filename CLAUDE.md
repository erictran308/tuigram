# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

tuigram: a Telegram *user* client (not a bot) for the terminal, built on TDLib (`tdlib-rs`) and ratatui, with vim-style modes. Published on crates.io as `tuigram-cli` (the name `tuigram` was taken); the binary is `tuigram`.

## Never run the app against the real session

The data directory holds the user's logged-in Telegram session: the platform app-data dir (`tuigram --help` prints it), or `TG_DATA_DIR` if set (e.g. `./.tdlib`). Running the binary reads their chats and sends read receipts (`view_messages`) to real people. Do not `cargo run` to check a change; verify with tests that render into ratatui's `TestBackend` (see existing tests in `src/ui/`). Ask the user to run the app when a change needs to be seen live, or `cargo run -- --demo`, which never starts TDLib.

## Commands

```sh
cargo build
cargo test                       # all tests
cargo test search_matches        # tests whose name contains the string
cargo clippy --all-targets       # keep it warning-free
cargo fmt
cargo install --path .           # puts `tuigram` on PATH (~/.cargo/bin)
cargo package --list             # check what would be published
cargo publish --dry-run
```

The first build downloads a prebuilt TDLib and links it statically (tuigram's default `download-tdlib` feature and tdlib-rs's `static`; tdlib-rs's own build script does the linking). tuigram's `build.rs` doesn't use tdlib-rs: as a build dependency it was built for the build machine, and a cross-compiled release (Windows ARM64 on an x64 runner) couldn't link it against the target's TDLib. Release builds use `--no-default-features --features local-tdlib` with `LOCAL_TDLIB_PATH` set to the zip the workflow checked, so tdlib-rs's build script downloads nothing. Static linking is deliberate: dynamic linking crashed the build script under clippy/rust-analyzer.

Config (`config.rs`): API credentials may never be committed or end up in the published crate (both are public). Release binaries get tuigram's own key at compile time instead: `.github/workflows/release.yml` (run by pushing a `v*` tag) passes the `TUIGRAM_API_ID` / `TUIGRAM_API_HASH` repository secrets, and `build.rs` writes them XORed with a per-build random mask to `$OUT_DIR/built_in_keys.rs` (so the hash is never plain text in the binary), which `config::built_in_keys` unmasks; `cargo install` builds have none. `cargo binstall tuigram-cli` installs the release binary instead (`[package.metadata.binstall]` in `Cargo.toml`, with its from-source and QuickInstall fallbacks off, since those would have no key), so release asset names and the `v<version>` tag must stay as `pkg-url` expects, and a release must be up before `cargo publish`. At runtime the key comes from `TG_API_ID` / `TG_API_HASH`, else `settings.toml`, else the built-in one, else the login screen asks for one (`LoginStep::ApiId` / `ApiHash`) before TDLib gets its parameters. If Telegram rejects the key in use, the login screen asks for another and a new TDLib client starts with it (`App::reject_api_keys`). `TG_DATA_DIR` overrides the data directory, which holds the TDLib database, downloaded files, `tdlib.log` and `settings.toml`; it's set to 0700 on every start. `TG_*` settings can also come from `.env` in the working directory, in development builds only (`cfg!(debug_assertions)`; see `.env.example`): `config::load_dotenv` reads only that directory and only `TG_*` keys, into a map `config::var` falls back to, and never sets process environment variables (so a `.env` in an untrusted folder can't set `LD_PRELOAD` for the programs tuigram starts). Release builds ignore `.env`, since one shipped in a cloned repository could pick, or supply, the folder the session is kept in. A `TG_DATA_DIR` on another machine is refused, and on Unix one set anywhere must have only private or root-owned sticky folders above it (`config::private_place`).

## Releasing

Release binaries carry tuigram's API key, so they're built only by `.github/workflows/release.yml`, from the `TUIGRAM_API_ID` / `TUIGRAM_API_HASH` repository secrets (Settings → Secrets and variables → Actions). Order matters: `cargo binstall` looks for the GitHub release of the version it finds on crates.io, so the release must exist before `cargo publish`.

1. Bump `version` in `Cargo.toml`, run `cargo build` (updates `Cargo.lock`), then tests, clippy, `cargo fmt --check` and `actionlint`.
2. Commit and push `main`.
3. Write a short changelog (a few bullets, for users) to a file outside the repo, then `git tag -a vX.Y.Z --cleanup=whitespace -F <file> && git push origin vX.Y.Z` (without `--cleanup`, git drops `#` lines such as Markdown headings). The workflow builds six targets (Linux/macOS/Windows × x86_64/ARM64) and, only if all succeed, creates the GitHub release with the archives, `SHA256SUMS` and a provenance attestation. The release notes are the tag's message followed by GitHub's "Full Changelog" link. About 15–20 minutes.
4. Once `releases/download/vX.Y.Z/SHA256SUMS` exists: `cargo publish`, then `cargo clean -p tuigram-cli`. Publish (and `--dry-run`) check-builds the packaged copy in `target/package/` into the shared `target/`, which leaves `cargo build`/`cargo run` tracking that copy's sources: later edits to `src/` stop rebuilding the binary until it's cleaned.

When `tdlib-rs` changes in `Cargo.lock`, update `TDLIB_RS_VERSION`, `TDLIB_VERSION` and every target's `tdlib_sha256` in the workflow (the zips are at `github.com/FedericoBruzzone/tdlib-rs/releases`); the build stops until they match. To build a binary with a key baked in locally, set the same variables: `TUIGRAM_API_ID=… TUIGRAM_API_HASH=… cargo build --release` (both or neither, or build.rs fails).

## Security

Everything another Telegram user sends is untrusted: text, names, chat titles, file names, links, files, images.
- Text that is shown or copied goes through `text::clean` (control characters other than `\n`/`\t`, bidi overrides and marks, and invisible characters terminals and the layout disagree on, such as the Hangul fillers of "invisible" names; joiners and variation selectors stay). `Msg` text gets it in `normalize`, which keeps link ranges in step. One-line snippets and chat-list previews keep at most 300 characters.
- Links and files open through `open_externally` (the `open` crate, ShellExecute on Windows), never a shell: `cmd /C start` would run what follows a `&` in a link. Downloaded files get the OS "from the internet" mark (`mark_downloaded`), whether opened or copied with `y`, and only `SAFE_TO_OPEN` types open without a `Confirm`; so do links whose text differs from their URL (`Link.disguise`, kept when the same URL also appears plainly). A link's `Confirm` shows its host on its own line, cut from the left so the site's name stays (`link_host`). A `Confirm` ignores `y` for `CONFIRM_GRACE` after it comes up, and a download finishing while a popup, prompt or the composer is in use waits for Enter instead of popping one up (`App::busy`). Sixel and iTerm2 images aren't drawn under popups (`Images::paints_over`).
- Images decode within `images::limits` (stickers within 1024 px), at most `MAX_BUILDING` at once, and a panic in a decoder only marks that image broken (`images::panic_is_contained`, checked by the panic hook). Image events carry `Images::generation`, so ones from a logged-out session are dropped. Byte slicing of message text uses `.get()` or ranges known to be on char boundaries.
- Read receipts go out only from `App::mark_seen`, when the chat pane and the terminal window have focus and the view is on the newest message (`App::watching`). Where the terminal never reports focus (tmux without `focus-events`, a detached session), a key within `IDLE_AFTER` stands in for it, so nothing is marked read while nobody is there; where it does, a key within `AWAY_AFTER`. Idle time is the longer of the monotonic and the wall clock (`App::idle`), since the monotonic one stops while the computer sleeps. While a jump to an older message loads (`Page::Around`), nothing is watched: a new chat starts out following the newest, and what arrives before the page would otherwise be marked read unseen. A chat or topic with unread messages opens at the first of them (`OpenChat::open_at_unread`: `at_newest` off, so nothing arriving meanwhile is taken, and `first_page`, an `Around` page of where you read to), so none is read until the cursor gets to the newest; `OpenChat::reached` then follows new ones once a page reaches the chat's newest message (`Chats::last_message`, `Topic::newest`). Ctrl-o back to a chat you left on its newest doesn't override that (`App::jump`, `entered`). A topic TDLib hasn't described yet (opened from a link) isn't watched at all until it has, and then opens at its first unread message (`App::topic_known`). Deleting the message under the cursor moves it to the next one, never back to following the newest (`OpenChat::remove`). Nothing is watched under the `I` popup either, which is as tall as the pane (`App::looking_at`; `cover_unseen` too). The one other receipt is for a message that mentions you or answers yours (`Msg.mention`, TDLib's `contains_unread_mention`), once the cursor is on it (`App::mention_seen`): the same presence, the message pane with the keys and nothing over it (`App::busy`), not in a secret chat (viewing it reads up to it, which would start the timers of the unread ones before it, unseen), and not a voice or video message nobody played (`Msg.unplayed`: seeing it isn't playing it). Telegram reads a mention only when that message is viewed, not when the chat is read past it; as in its apps, `gm` to a mention reads the messages before it too, unshown. Don't call `view_messages` anywhere else.
- Online status goes out only from `App::update_online` (window focused and a key within `IDLE_AFTER`), and `Tg::close` sets offline first. SIGHUP, SIGTERM and a terminal that stops working quit through `App::hang_up` (which also stops read receipts), and the panic hook sends offline with `tg::offline_now` (TDLib's `td_send`, without the async runtime). Don't set the `online` option anywhere else.
- Typing status goes out only from `App::set_typing`: while the composer has text after an edit (again every `TYPING_EVERY`), and a stop when it's emptied, Insert mode is left or the chat changes. Sending the message ends it without a stop. Don't call `send_chat_action` anywhere else.
- Files go out only from what's in `OpenChat.attachments`, which the composer lists by name and size (past three, the last row names the rest), and only on Enter, and not if one was swapped between being listed and Enter (`Attachment::swapped`; TDLib opens the file later, so a swap after Enter isn't caught). An attachment is named after what's sent: a link's target, not the link. A paste attaches only absolute paths of existing files, as written (no `~`), so a word that happens to be a file name, or a path quoted in a message, stays text; `\\server\share` paths are never even looked at (`attach::on_another_machine`), since on Windows that hands the server the user's login hash. The clipboard is read only on `p` / Ctrl-v, and a paste that comes back after the chat or forum topic changed (`Pasted.place`), or once the keys went to the chats or topics, is dropped, so it can't force Insert mode under an Enter meant for something else.
- Files tuigram writes or deletes: `settings.toml` (it can hold API keys) is written 0600 through a rename (`Settings::save`); `clean_outbox` deletes only `pasted-<digits>.png/jpg`, since `TG_DATA_DIR` can come from `.env`; `--demo` writes only into a new 0700 temp folder (`demo::new_private_dir`). Theme files are read only if they're plain files under 64 KB (`theme::read`), so a link to `/dev/zero` or a pipe can't hang startup.
- Notification text goes through `notify::escape`, which cleans it, flattens it to one line and replaces `;` so a message can't end the escape code early.
- A panic restores the terminal and exits (hook in `main`), printing the message through `text::clean`.
- TDLib's OpenSSL is told not to read a configuration file before TDLib starts (`tg::no_openssl_config`): its compiled-in folder may be one another account can create.
- Inside tmux, ratatui-image switches the pane's `allow-passthrough` on; `tmux::save` and `tmux::restore` put the pane's own value back on exit and in the panic hook.
- A t.me link in a message opens in tuigram only if its real host is Telegram's (`picker::telegram_link`), and nothing it leads to happens without a key: a chat just opens, an invite asks, a bot's start link goes to the browser. A link preview names the link's host from its URL, not the name the page gives itself, and shows only if it's of one of the message's own links (a sender can attach a preview of another page, and Enter opens the text's links).
- Joining a chat, from an invite link or with `i` in a public group you're not in, always goes through a `Confirm` naming it, with Telegram's verdict (`Confirm.badge`) on a styled line of its own above the name, so a long or spoofed name can't hide or fake it. Forwarding sends on Enter in the picker, to the chat under the cursor, which the picker keeps by identity (`ChatPicker::current`), not row, since chats reorder as messages arrive. A chat looked up with `s` opens only if the answer comes while nothing holds the keys (`App::busy`); writing, a popup or Esc drops the lookup (`App.finding`), and `open_chat` closes popups about the previous chat's messages.
- A bot's buttons (`buttons.rs`) are its words: their labels are cleaned onto one line, and they're cut to fit where they're drawn, so a URL button always asks first (its `Link.disguise` is its label, even one that looks like the URL), only http(s) and cleaned `tg:` links can be pressed, and a reply button's words go out with `Tg::send_plain`, not as Markdown. The popup says in full what Enter on the button under the cursor does (`Button::describe`: the whole text a reply button sends, the host a link goes to), ignores Enter for `CONFIRM_GRACE` after it comes up (`ButtonMenu.shown`), so a double or held Enter can't press the first button, and has no number keys. Buttons that would share your phone number, location or password, pay, or open a web app or game are `Press::Unsupported`. A bot's answer to a button (`TgEvent::BotAnswer`) is a toast; an alert is a `Notice` popup that only Enter or Esc closes, and a link in the answer opens through the same disguised-link `Confirm`; neither pops up while `App::busy` or after its chat, or forum topic, was left (`TgEvent::BotAnswer.topic`).
- Secret chats (`secret.rs`): TDLib accepts incoming ones by itself once `use_secret_chats` is on, and one lives on whichever of the user's devices accepts it first, so `Tg::accept_secret_chats` tells Telegram whether this session takes them (`toggleSessionCanAcceptSecretChats`): `Settings.accept_secret_chats`, off by default, applied at `authorizationStateReady` and when ticked in `?`, one request at a time with the latest wish (`AcceptSecretChats`), so a quick tick and untick can't end applied backwards. One taken although it's off (`notificationTypeNewSecretChat`) is said in the status bar. A secret chat's 🔒 is drawn on `colors.secret` (`ui::lock_spans`), which a name starting with 🔒 can't imitate, and its composer's border says "secret chat". It opens at the first unread message (`OpenChat.unread_after`, `go_to_unread`), since `view_messages` of the newest reads them all and starts their timers. Text sent in a secret chat has link previews off (`Tg::send_text`'s `secret`): Telegram's servers make them, seeing the link. A secret chat's notifications say only "Secret chat: New message". `:secret` and ending one (`:leave`, `Confirmed::EndSecret`) ask first; nothing is sent in one that's pending or closed (`App::cant_send`), nor forwarded out of one.
- Media shown only while open (TDLib's `is_secret`: view-once photos, short self-destruct timers): a photo is covered in its bubble (`Msg.hidden`, the open body kept aside) and has no `file`; videos, GIFs and video messages have neither preview nor file, and say to watch them on the phone (`messages::ON_PHONE`). Nothing whose timer starts on opening (`Destruct.on_open`, `app::opens_once`, voice messages too) is opened or copied as a file: another app would keep it. tuigram plays voice messages itself, so those play. Enter uncovers a photo (`OpenChat::uncover`) and downloads it; `openMessageContent`, which tells the sender it was opened and starts its timer, goes only once it's downloaded and still shown (`OpenChat.opening`, on `TgEvent::Downloaded`), never for your own or one still sending. It's covered again once the cursor leaves it, the message pane loses the keys, or nobody is there (`App::cover_unseen`, `App::present`, as for read receipts), and a view-once one that expired as it opened stays only until then; with sixel or iTerm2 the screen is cleared once it's covered, so no pixels stay behind (`App.shown_viewing`). `y` copies nothing TDLib says can't be saved (`Msg.saveable`). `:key` shows the open chat's key and closes if it changes; a window too small for all of it asks for a bigger one rather than show part.
- Voice messages play in tuigram, never in another app (`voice.rs`): only Opus in Ogg (`Voice.ogg`; MP3 and M4A ones open elsewhere as before). The decoder is `src/opus`, a trimmed copy of the `opus-decoder` crate: its 0.1.1 release writes debug logs to fixed paths on every frame, so it isn't a dependency; keep the copy free of `std::fs`/`env`/`io` and printing, and `#![forbid(unsafe_code)]`. It panics on some packets a sender can make, so the whole playback runs in `images::contained` and a panic only says it can't be played. Files over `MAX_FILE` aren't downloaded (`Voice.size`) or read, and Ogg is read by `OggPackets`, not a general reader: the first stream only, packets up to `MAX_PACKET`, the comment header skipped unread, so a file can't make it hold much. `openMessageContent` for a voice message, which tells the sender it was played and starts a self-destructing one's timer, is decided on Enter (`OpenChat::tells`: someone else's, sent, not played; kept as `Playing.tell`) and goes from `App::on_voice` once sound is heard, not just queued (`Happened::Started` after `Sink::played`), even if the message was unloaded meanwhile. A menu plays a voice message by its id (`Target::Voice`), never by the cursor, which may have moved; `openable_file` keeps media seen only while open out of menus otherwise. A download that finishes while nobody is there (`App::present`) doesn't start playing. Playback stops on switching chats, logging out, quitting, or the message being deleted. On Linux, libasound is loaded with `dlopen` when something first plays (`sound.rs`), so tuigram still starts without it; its error printer is replaced, and stderr goes to /dev/null while the device opens (`quietly`), since the libraries it loads for PulseAudio or JACK print their own over the screen.
- Chats keep Telegram's verdicts on whom they're with (`chats::Badge`: scam, fake, verified or official, from `updateUser` / `updateSupergroup`), shown after the name in the list, the chat's title, a forum's topics pane and notifications. Titles are cut to leave room for the verdict, never the verdict itself (`ui::messages::draw`, `ui::topics::draw`).
- Service messages (`service.rs`) are sentences of `service::Part`s: tuigram's own words drawn muted, like a date, and the names and titles people picked in colors of their own (you in yours), each on one line (`ui::messages::service_lines`), so a name like "Thu 8 Oct 2026" or "Bob removed Alice." can't pass for a date or an event. A topic's preview names its sender the same way, so someone named "You" doesn't pass for you.
- The chat info popup (`I`, `:info`; `info.rs`, `ui/info.rs`) shows what people wrote about themselves or their group: bios, descriptions and admin titles are cleaned (titles on one line, at most `MAX_TITLE` columns), the chat's title keeps its verdict as elsewhere, and members' names are drawn with theirs (`Chats::user_badge`). You're in `colors.primary` with "(me)" muted and apart, and admin titles are muted, never the accent Telegram's ✓ is drawn in, so a name or title can't pass for either. Enter on a member only opens the chat with them (`createPrivateChat` through `App.finding`); nothing is sent. While it's up, pastes and a late `e` answer are dropped rather than put Insert mode under it. Members come a page at a time, at most `info::MAX_MEMBERS`, and a page that adds nobody ends the paging (`ChatInfo::add_page`).
- The photo viewer (`viewer.rs`) hides the whole chat, so while it's up nothing is marked read (`App::watching`), notifications aren't held back (`App::sees`), opening it pins the cursor on the photo rather than following new messages (`App::view_photo`, so an Enter after closing it isn't on something that arrived unseen), and pastes and a late `e` answer are dropped rather than put Insert mode under it. It never takes media shown only while open (`PhotoView::of`), `o` doesn't hand on what Telegram says can't be saved, and keys with Ctrl or Alt do nothing in it (Ctrl-o isn't `o`). At most `MAX_LARGE` window-sized encodes are kept (`images::large`): kitty's keeps all it sent, tens of MB each.
- Forum topics (`topics.rs`): what's done in a topic stays in it (history, sending, typing, search, pinned, read receipts, pastes and bot answers all carry the topic, and `gd` to a message of another topic keeps the view rather than landing near it). Others' activity can't make tuigram ask TDLib for much: `getForumTopic` goes only for a topic a new message is in that isn't loaded, one whose newest message was deleted, or one read partway (not for reactions, mentions or the like), once until answered; `updateForumTopicInfo` for a topic not loaded asks nothing (TDLib announces each topic a page brings before the page); paging stops at a page that adds nothing new; and page answers carry a request number counted across visits (`App.topics_asked`).

## Architecture

**Event loop (`app.rs`, `App::run`).** One `tokio::select!` over: TDLib events, finished image encodes, terminal key/paste/focus events, and the quit deadline. Each wake drains the TDLib backlog, then the loop redraws. All state lives in `App`; nothing else mutates it.

**TDLib wrapper (`tg.rs`).** A plain thread blocks on `tdlib_rs::receive()` and forwards updates as `TgEvent::Update`. Every event is tagged with its client id (`tg::Tagged`), and `App::on_tagged` drops events from a client that has been replaced. Every request is spawned as its own tokio task and never awaited by the UI; results come back as `TgEvent`s (`History`, `Found`, `ChatsLoaded`, `Downloaded`, `Error`). Responses carry what was asked for (chat id, `Page`, query) so the app can drop ones that went stale while in flight. TDLib takes its parameters only at startup, so logging out (`:logout`, the session ending elsewhere, Esc out of a QR login) or switching API keys closes the client, and on `authorizationStateClosed` `Tg::reopen` starts a new one after `App::forget_session` drops the old session's state. TDLib logs go to `tdlib.log`, set up with its synchronous `td_execute` (declared by hand, since tdlib-rs doesn't wrap it) before the first client exists; otherwise TDLib prints to stderr over the terminal.

**Chat list (`chats.rs`).** Rebuilt purely from TDLib updates (`updateNewChat`, `updateChatPosition`, …). Each chat keeps its position in every list it's in (`Chat.positions`, by `chats::List`: `Main`, `Archive` or `Folder(id)`; an order of 0 takes it out), and the list shows one of them (`Chats::shown`). Your folders come from `updateChatFolders` (`Chats::set_folders`, with where "All" goes among them), and `Chats::tabs` makes them tabs over the list, the archive last once a chat in it is known, none without folders or an archive; each tab has its unread unmuted chats from `updateUnreadChatCount` (`Chats::set_unread_in`). Tab / Shift-Tab in the list go round them (`App::switch_list`), the cursor on the folder's first chat. Order is pinned first (`Chat::pinned`, in the list shown), then unread, then TDLib's per-list `order`; `p` pins or unpins in the list shown (`toggleChatIsPinned`) and `m` mutes for good or unmutes (`Chats::with_mute`, `setChatNotificationSettings`), on Telegram. A chat is muted by its own `mute_for` or its kind's default (`updateScopeNotificationSettings`, `Chats::muted`), drawn as 🔕 after its name and a grey unread count; a chat with unread messages that mention you (`Chat.mentions`, from `unread_mention_count`, `updateChatUnreadMentionCount` and `updateMessageMentionRead`) has an `@` before its count, which a mute doesn't grey; `refresh()` re-sorts once per frame when dirty and applies the `/` title filter. Selection is stored by chat id, not index, so it survives reordering. All chats of the main list, and of each list once shown (`App.wanted_lists`), get loaded in the background (loop on `ChatsLoaded`, per list) because unread-first sorting needs them all; once the main list is in, one page of the archive says whether it gets a tab. `Chats::listed` and the pickers still mean the main list. `ui/chat_list.rs` draws each chat as two rows plus a blank one, with its photo (`ChatPhoto`: TDLib's 160 px `small` file) cut to a circle, else a plain square of `colors.names[Chats::accent]` (`colors.primary` for Saved Messages). The selected chat's rows are highlighted by hand, not with List's `highlight_style`, so the blank row stays blank. Photos are left out with halfblocks (too coarse) and in a list under `MIN_WIDTH_FOR_PHOTOS` columns. `updateChatAction` fills `Chat.activity` (who is typing, recording, …); TDLib itself sends the stop when the message arrives or after 5.5 s without a repeat, so there are no timers. While it's set, `ui::activity` words it ("typing…", "Alice is typing…") in place of the chat's last message and after the open chat's title.

**Open chat (`messages.rs`).** `OpenChat.messages` is a `BTreeMap` keyed by message id (chronological) and is always one unbroken stretch of history. `Page` (`Latest`/`Older`/`Newer`/`Around`) says what to fetch; `Latest` and `Around` replace the stretch, since they may not join up. `loading: Option<Page>` is the one request in flight, and pages for any other request are ignored. `at_newest` is false after jumping to an old message (search): new messages aren't inserted then, and moving down loads `Newer` pages. `selected: None` means "on the newest message, follow new arrivals"; while it is, only the newest `MAX_FOLLOWED` messages stay loaded. Scroll position is a `ScrollAnchor` (message id + line offset) so it survives older pages loading above.

Replies (`Msg.reply_to`) show the message they answer above their text: the loaded one if it's there, else one fetched with `getRepliedMessage` after the frame (`OpenChat::missing_replied`), cached in `OpenChat.replied` by the reply's id. `r` sets `OpenChat.reply`, which the next sent message answers. `gd` jumps from a reply to what it answers (`OpenChat::replied_jump`), leaving the reply in `App.jumps` for Ctrl-o to return to. `App.jumps` is vim's jump list, as a back and a forward stack of `Jump`s (a chat, and the message the cursor was on, `None` for the newest): `App::open_chat` leaves the chat before there, however it was opened, and Ctrl-o / Ctrl-i (`App::jump`) move between them with `App::enter_chat`, which doesn't. Terminals without the kitty keyboard protocol send Ctrl-i as Tab, so Tab in the message pane goes forward too; in the chat list it switches folders.

`e` edits a message: `App::edit_selected` rules out what `OpenChat::cant_edit` can tell (still sending, no text), then asks TDLib (`getMessageProperties.can_be_edited`, `TgEvent::Editable`), which knows whose it is and the chat's time limits. `OpenChat.editing` then holds it, with the composer's draft and reply, which `App::end_edit` puts back once the edit is saved or cancelled. Messages, captions and edits are sent with their Markdown made formatting (`tg::markdown`, TDLib's `parseMarkdown`, run synchronously through `td_execute` so messages still go out in order; `tdlib.log`'s verbosity 2 keeps their text out of the log). `check_editable` also fetches the message and writes it as Markdown (`tg::to_markdown`, `getMarkdownText`) for the composer, `Editing.original`, so saving keeps its formatting and an untouched edit sends nothing; only formatting Markdown can't write (underline, custom emoji, `EditText::loses`) asks first (`Confirmed::Edit`). If the message can't be fetched, it's edited as plain text, which asks first if `Msg.formatted`. Text messages go through `editMessageText`, captions through `editMessageCaption` (`Msg.editable`). `updateMessageEdited` sets `Msg.edited`, shown as "edited" before the time.

An album (`Msg.album`, TDLib's `media_album_id`) of photos or videos is drawn as one bubble, as in Telegram (`ui::messages::albums`): the reply quote over the first photo, and the caption and the time under the last, though Telegram keeps the caption on the photo it was sent with. Each photo is still its own message for the cursor, and `e` anywhere in the album edits that caption (`OpenChat::edit_target`).

TDLib `Message`s are converted to `Msg` once on arrival (`body()`): display text, inline `Preview`, the file Enter opens, and links. Only http(s) links are kept (so a crafted link can't open local files/apps), and TDLib entity offsets are UTF-16 code units, converted to byte ranges.

Formatting entities become `Msg.styles` (`messages::styles`): nested and overlapping ones are cut into non-overlapping `Styled` stretches, shifted after a caption's label and moved by `normalize` like link ranges, and `ui::messages::line_spans` paints them (`Paint`; code in `colors.code`). A spoiler draws as one `⠿` per column until Enter reveals it (`Msg.revealed`, `OpenChat::reveal_spoilers`, the whole album), so revealing moves nothing. Snippets, chat previews and notifications never reveal one (`hide_spoilers`; `chats::content_text` hides them, `content_text_as_sent` keeps them for the bubble). `Msg.forwarded` (`Origin`) puts "Forwarded from …" above the bubble, once per album.

**Modes and keys.** `Focus::Chats` / `Focus::Topics` / `Focus::Messages` are Normal mode; `Focus::Input` is Insert mode (the composer). `on_key` routes to the first modal layer that's open, in this order: the confirmation popup (`Confirm`, only `y` goes ahead), a bot's alert (`Notice`), a secret chat's key (`KeyView`), the photo viewer (`PhotoView`), settings popup (`?`: Enter or Space picks a theme or toggles a setting and saves it at once, `App::change_setting`), delete popup (`d`), reaction popup (`R`), vote popup, bot button popup (`ButtonMenu`), pin popups (`PinMenu`, `PinnedMenu`), the self-destruct timer popup (`TimerMenu`), the chat info popup (`ChatInfo`), open-file menu, chat picker (`f` / `s`), resize mode (`App.resizing`, Ctrl-r: `h`/`l` change `Settings.chat_list_width`, or `Settings.topics_width` when Ctrl-r was pressed in a forum's topics, `Resizing::Topics`; saved on Enter), the status bar prompt (`/` search or `:` command, `PromptKind`), the sticker panel, Insert mode, Normal mode. `Settings.chat_list_side` can put the chat list on the right; then `h` and `l` swap (opening a chat, going back to the list, resizing) so they follow the screen, and the status bar hints swap with them. `:` commands (`app::Command`) only run by their full name, so a typo can't log anyone out; Tab / Shift-Tab put in the full name of one that starts with what was typed, going round them as vim does (`Prompt::complete_command`, `Prompt.tabbed`), and Enter still runs it. Since Tab can put `logout` in, it asks first too (`Confirmed::Logout`). The status bar shows the mode and the key hints for the current state, and `?` lists every shortcut (`SHORTCUTS` in `ui/help.rs`), so update both when adding keys.

**Forwarding and finding chats (`picker.rs`).** `f` opens a `ChatPicker` with `Purpose::Forward` (the bubble's sent messages, `OpenChat::forward_ids`) listing your chats, Saved Messages first, filtered as you type by title or @username (`Chats::matching`, in Telegram's order, not unread-first); Enter calls `Tg::forward` (`forwardMessages`, keeping "Forwarded from"). `s` opens it with `Purpose::Open`: a typed `@username` or t.me / `tg:` link comes first (`picker::typed`), then your chats, then contacts and public chats from `Tg::find_chats` (`searchContacts` and `searchPublicChats`), asked once typing pauses for `SEARCH_AFTER` (the run loop wakes for `ChatPicker::search_at`) and dropped if the query changed meanwhile. Keys type into the search; arrows, Ctrl-n / Ctrl-p and Tab move. Lookups (`Tg::find_username`, `find_link`, `find_private_chat`) answer with `TgEvent::ChatFound`, kept only if it matches `App.finding`, which opening any chat clears; a link to a message opens the chat around it. An invite to a chat you're not in comes back as `TgEvent::Invite` and asks first (`Confirmed::JoinLink`). A chat opened this way may not be in the list (`Chats::listed`); in a public group or channel you're not in (`Chats::joined`, from `updateSupergroup`'s status), `i` asks to join (`Confirmed::Join`). Usernames come from `updateUser` / `updateSupergroup` (`Chats::set_username`).

A t.me link in a message (`picker::telegram_link`, judged by its real host) opens through the same lookup (`Finding.link`); a kind tuigram doesn't open (a sticker set, a bot's start link: `Missed::Elsewhere`) goes to the browser as before, warning first if disguised. `:leave` asks first (`Confirmed::Leave`), only for groups and channels.

**Bot buttons (`buttons.rs`).** A message's `reply_markup` becomes `Msg.keyboard` (`Keyboard::of`): inline buttons, which act on the bot's message, or reply buttons (`Keyboard.reply`), which send their words; `updateMessageEdited` brings new ones (`OpenChat::set_keyboard`). The bubble draws inline buttons last, under the time, as `[ words ]`, a row per row sharing the bubble's width (`ui::messages::button_row`), and reply buttons as one faded line, `⌨ [Yes] [No]`. Enter on the message opens `ButtonMenu` (after spoilers and polls), its rows then a row each for the message's file and links, so Enter still reaches them; `App::press_button` does what `Press` says: `Tg::press_button` (`getCallbackQueryAnswer`) for a callback, `open_target` for links and files, a lookup for `tg:` links and users, a copy, or `Tg::send_plain` (answering the bot's message in a group). An edit or deletion of the message closes the popup.

**Unread messages and mentions.** A chat or topic opened with unread messages opens at the first of them, as in Telegram (`App::enter_chat` / `enter_topic` set `OpenChat.unread_after`, and `show_messages` loads `OpenChat::first_page`, an `Around` page; with nothing read yet, the newest page and older ones until the first), and keeps where you'd read to (`OpenChat.unread_line`, from `last_read_inbox_message_id`, the topic's for a topic), and "Unread messages" is drawn across the pane on `colors.selection` (no sender's row has a background that wide, so a name over a sticker can't pass for it) over the first message after it from someone else (`OpenChat::first_unread`, `ui::messages::unread_line`), once the loaded messages reach back to it; it breaks a block like a date, and stays until the chat is left. `gu` goes there (`App::go_to_unread`, else the first unread now), leaving a `Jump`: at once if it's loaded (`OpenChat::unread_loaded`), else with an `Around` page of where you read to, after which `OpenChat::go_to_unread` puts the cursor on it (`OpenChat.unread_after`, as for a secret chat). `gm` asks TDLib for the unread mentions (`Tg::mentions` with `tg::Mentions::Unread`: `searchChatMessages` with `searchMessagesFilterUnreadMention`, in a topic narrowed by its `topic_id` if TDLib can't) and goes to the oldest (`App::on_mentions`, dropped if the keys went elsewhere or it answers another question, `OpenChat.mentions_asked`); seeing it reads it (see Security), so `gm` again goes on to the next. With none unseen, `gm` goes to the mention before the cursor and `gM` to the one after it, seen or not (`Mentions::Before` / `After`: `searchMessagesFilterMention`, a page from the cursor's message, `Mentions::pick`). In the chat list or topics, `gm` opens the one under the cursor first. `G` while a page around an older message loads goes to the newest instead (`App::jump_to_newest`). The status bar hints `gm` while there are some (`App::unread_mentions`).

**Chat info (`info.rs`, `ui/info.rs`).** `I` (or `:info`) opens `ChatInfo` about the chat under the cursor in the list, the forum in the topics, or the chat open (`App::info_chat`), and asks `Tg::chat_info`: `getUser` and `getUserFullInfo` for a person (phone, bio, a bot's description, groups in common), `getBasicGroupFullInfo` for a basic group (its description and all its members), `getSupergroupFullInfo` for a supergroup or channel (description, member count, and whether you can see its members: `Roster`). A supergroup's members come from `getSupergroupMembers` (recent first, `info::MEMBERS_PAGE` at a time, `TgEvent::ChatMembers`) as the cursor nears the end (`ChatInfo::page_to_ask`). The popup shows the title, kind and count or last seen, @username or t.me link, phone, bio, then the members with when they were last seen and their role or admin title; `j`/`k`, `g`/`G` and Ctrl-d/u move, Enter opens your chat with the one under the cursor (`App::write_to_member`), Esc closes it. It's a popup, not a pane, since a terminal is too narrow for one beside the messages.

**Pinned messages (`pins.rs`).** `Msg.pinned` comes from `is_pinned` and `updateMessageIsPinned` (`OpenChat::set_pinned`), shown as 📌 before the time. `OpenChat.pinned` is the chat's pinned messages, newest first (`Pinned`: id, sender, date, snippet), fetched when a chat opens and again after every pin update (`Tg::pinned_messages`, `searchChatMessages` with `searchMessagesFilterPinned`, up to `PINNED_PAGES` pages); answers carry `OpenChat.pinned_asked` so an older one is dropped, and `set_pinned` changes the list at once meanwhile. The newest shows in a bar over the messages, with a rule under it (`ui::messages::pinned_bar`). `P` unpins a pinned message, else opens `PinMenu`, filled once `getMessageProperties.can_be_pinned` answers (`TgEvent::Pinnable`): for both or just you in a chat with one person, notifying or not in a group or channel, the cursor on the gentler choice (`PinMenu::allow`). `gp` opens `PinnedMenu`; Enter goes to the message, leaving a `Jump` for Ctrl-o, and `P` unpins it. Its cursor is kept by message id, not row, since anyone can pin or unpin while it's open; once its message is gone, Enter and `P` do nothing until it moves.

**Secret chats (`secret.rs`).** `updateSecretChat` (state, the key) goes into `Chats::set_secret` by secret chat id, and `Chat.secret_id` links a chat to it (`Chats::secret`, `is_secret`). They show a 🔒 and `colors.secret` in the list, the title and the `s`/`f` picker (where they're "secret chat", since the title is the person's name), and the title says "waiting for … to come online", "ended", or the timer (`Chats::auto_delete`, from `updateChatMessageAutoDeleteTime`). `:secret` (`Tg::start_secret_chat`, `createNewSecretChat`) opens the new chat through `App.finding`; `:timer` opens `TimerMenu` over the open secret chat, named in its title (`setChatMessageAutoDeleteTime`, sent only if it changes, since each change posts a message, and kept at once), with the chat's own timer among the choices if the other side set an unusual one; `:key` opens `KeyView`, the 12×12 picture of `key_hash` in TDLib's four colors, two columns a pixel, with its first 32 bytes in hex (`key_picture`, `key_hex`); `:leave` closes it and deletes its history here (`Tg::end_secret_chat`). Search uses `searchSecretMessages` for words (paged by `Found.next_offset`), `searchChatMessages` otherwise, and `from:` is refused. Pinned messages aren't asked for. A message's self-destruct timer is `Msg.destruct` (`Destruct`: its length, whether it starts on open, and when it ends, from `self_destruct_in`), drawn as "🔥 30s" before the time, then counting down; TDLib sends no update when a timer starts, so the app mirrors it: reading (`App::mark_seen`, `updateChatReadOutbox`) starts those of read messages (`OpenChat::start_timers`), and opening a photo (`openMessageContent`, `updateMessageContentOpened`) its own (`OpenChat::start_timer`); the run loop wakes when a countdown changes (`OpenChat::next_tick`). TDLib deletes the message when it runs out.

**Forum topics (`topics.rs`, `ui/topics.rs`).** A supergroup with `is_forum` (`Chats::set_forum`, from `updateSupergroup`; `Chats::is_forum`) opens as a forum: `App::enter_chat` hands it to `App::enter_forum`, which keeps it open in TDLib and puts its topics (`App.forum`, a `Forum`) in a pane between the chat list and the messages, `Focus::Topics`, `Settings.topics_width` columns wide (never more than half of what the chat list leaves). `getForumTopics` fills it a page of `topics::PAGE` at a time as the cursor nears the end (`Forum::page_to_ask`; answers carry the offset asked, so stale ones are dropped), pinned first, then TDLib's `order`; the cursor is kept by topic id. Enter or `l` opens a topic (`App::open_topic`, leaving a `Jump` with its `topic`; `enter_topic` keeps the chat open in TDLib): an `OpenChat` with `topic` set, whose history comes from `getForumTopicHistory` and whose sending, typing, search, pinned messages and read receipts (`viewMessages` with `messageSourceForumTopicHistory`) all carry the topic (`OpenChat::place`; `History`, `Found` and `Pinned` answers carry it too, so one for the topic left is dropped). `h` / Esc go from a topic's messages back to the topics (`App::left_of_messages`), then to the chats. Only some changes come as updates: `updateForumTopicInfo` (name, icon, closed) and `updateForumTopic` (pinned, read up to, mentions); a new message moves its topic up and counts as unread unless yours (`Forum::add_message`, which takes `topics::Arrived`, since a TDLib `Message` can't be built in tests), and anything only TDLib can work out (an unread count read partway, a topic not loaded, a topic whose newest message was deleted) is asked for with `getForumTopic` (`App::ask_topic`, once until answered). Messages without a `topic_id` are in General (`Forum::topic_of`). Topic names go through `one_line`, and icons are drawn in the theme's `names` color nearest Telegram's six (`Topic::accent`). A t.me link to a topic or a message in one opens it (`tg::Spot.topic`, from `messageLinkInfo.topic_id`).

**Polls, previews, last seen.** A poll (`poll.rs`, `Msg.poll`) is drawn as its bubble's text: the question, the answers, and once you voted or it closed, a bar and percentage each (a quiz marks the right answer ✓ and a wrong one of yours ✗). Enter opens `VoteMenu`; Space ticks answers in a poll that takes several, and a last row takes your vote back (`Tg::vote`, `setPollAnswer`); TDLib's `updateMessageContent` brings the new counts. A text's `link_preview` becomes `Msg.card`, drawn under the text: the link's host read from its URL (`link_host`, not the page's own `site_name`), the title, and `CARD_LINES` of description, with the page's picture (`Card.image`: an article's photo, a video's cover, the photo linked to, in TDLib's small size) on their left: `thumbnail_cells` keeps it `THUMBNAIL_ROWS` tall and its own shape, and `measure` adds a `PhotoSlot` for it, only where `Images::draws_photos` (not with half blocks). A one-on-one chat's title says "online" or when they were last seen (`Chats::seen`, from `updateUser` / `updateUserStatus`; `ui::messages::seen_label`), or "bot", unless they're typing.

**Completion (`complete.rs`).** After each key in Insert mode, `App::update_completion` looks at the word before the cursor (`complete::word_at`): `@name` in a group suggests the senders of the loaded messages, then members from `searchChatMembers` (`Tg::find_members`, once typing pauses for `complete::SEARCH_AFTER`), not you; `:sm` (two letters or more, after a space) suggests emoji by shortcode, offline, without joined ones. Tab replaces the word; arrows and Ctrl-n / Ctrl-p move; Enter still sends, so a suggestion is never taken by accident. Someone without a username is written `[Name](tg://user?id=…)`, which `tg::markdown` turns into a mention (and `to_markdown` writes a mention back that way for edits). `/` starting a message suggests the commands of the chat's bots (`OpenChat.commands`, asked once per open chat with `Tg::bot_commands` from the user's or group's full info; `complete::commands` adds `@bot` when the chat has several).

**Reactions (`reactions.rs`).** `Msg.reactions` comes from `interaction_info` on arrival and from `updateMessageInteractionInfo` (`OpenChat::set_reactions`); bubbles draw them as pills under the text, yours filled in (`colors.your_reaction`), with the time beside the last row. An album shows all its photos' reactions added up under the last one, and `R` reacts where it already has reactions, else on its first photo (`OpenChat::react_target`). `R` opens `ReactMenu` at once and fills it from `getMessageAvailableReactions` (`TgEvent::Reactions`): plain emoji only, none that need Premium, and no ZWJ sequences (❤‍🔥, 👨‍💻) unless already yours, since terminals disagree on their width. The cursor starts on your reaction, and Enter adds the emoji under it, or removes it if it's yours (`Tg::react`); TDLib then sends the update. `X`, in the chat or the popup, removes all yours from the bubble (`OpenChat::your_reactions`, every photo of an album). `/` in the popup searches names and GitHub shortcodes from the `emojis` crate, offline. `reactions::shown` adds U+FE0F to single-codepoint emoji Telegram sends without it (❤, ✍), so they're two columns everywhere; Telegram is always sent the emoji as it gave it. Custom-emoji and paid reactions show as `✦` / `⭐` with their count.

**Stickers (`stickers.rs`).** Tab in Insert mode opens `StickerPanel` (`App.stickers`) between the messages and the composer (`ui/stickers.rs`). It's part of Insert mode: `on_key` closes it whenever the focus leaves `Input`. It opens at once and fills in from TDLib: Recent and Favorites (dropped when empty, as in Telegram), then a tab per installed set (`getInstalledStickerSets`), whose stickers are asked for the first time the tab is shown (`StickerPanel::pending_set`). `/` searches with `getStickers` (installed first, then Telegram's suggestions); answers carry their query, so stale ones are dropped, and a paste while the panel is open goes into the search. The grid shows each sticker's thumbnail (`Preview::sticker_thumbnail`, a fraction of the download), or its emoji where there's none or the terminal only has halfblocks. Custom emoji are left out, and Premium stickers unless the `is_premium` option says you have it. Enter sends an `inputMessageSticker` by file id (`Tg::send_sticker`), answering `OpenChat.reply`, and leaves the composer's text alone. Animated stickers (TGS, WebM) show their still thumbnail, here and in messages.

**Search (`search.rs`).** `/` in the chat list filters titles live (local). `/` in a chat runs TDLib `searchChatMessages` over the whole history; `n`/`N` go to older/newer matches, and a match that isn't loaded is reached with an `Around` page. Filters typed among the words (`search::parse` into `search::Query`, kept as `MessageSearch.ask`; `MessageSearch.query` is what was typed): `from:` is `me`, `@username` or part of a name, which `App::resolve_sender` turns into a sender where it can (a name only among the loaded messages' senders, and only if it's theirs in full or nobody else's matches, since names are anyone's to pick; a username only if one person has it), else `Tg::search_messages` looks the username up (`searchPublicChat`; a chat id above 0 is a person); `has:` is TDLib's `SearchMessagesFilter`; `before:` / `after:` are local day starts, and since TDLib's search takes no dates, a `before:` search starts at `getChatMessageByDate` and both are applied to each page's dates (`tg::search_page`), so the total is then unknown. Only the words are highlighted. Tab in the `/` prompt goes round `search::complete`'s ways to finish the last word, with the `:` prompt's `Prompt::tab`. `search::find` gives case-insensitive byte ranges, used for both filtering and highlighting.

**Rendering (`ui/`).** `ui/messages.rs` measures every loaded message each frame (bubbles, wrapping, date separators, sender names except in channels; `measure`), picks the scroll window, then builds lines only for the messages in it (`Laid::lines`): a sender decides how many rows a message takes. Link and search ranges are looked up per line (`overlapping`), and they're kept in order. Your messages get ✓ after the time once sent and ✓✓ once read (`Chat.read_outbox`, from `updateChatReadOutbox`), except in channels and Saved Messages. Photos are not text: layout reserves blank rows (`PhotoSlot`) and `draw_photos` paints images over them afterwards. Once the date of the day at the top has scrolled away (`Laid::date_above`), it takes the pane's first row, in place of the row there, so nothing moves; when the cursor's message starts at the top, the rows move down one instead, so the date never hides it. `open.scroll` keeps the unshifted top, or the view would creep a row a frame. Service messages (`service.rs`, `Msg.service`: someone joined, was added or left, the group renamed, a message pinned…) aren't bubbles: `Service::sentence` names who did it when drawn ("Alice added Bob"), centered and muted like a date, with no time, and the next message names its sender again; the chat list shows `Service::label` ("[Joined the group]"), notifications the sentence. Names and titles in them are cleaned like any other text. Popups start with `ui::Cover`, not `Clear`: it also blanks a two-column character (an emoji in a name, a 🔒) that the popup's left edge cuts in half, which ratatui's diff would otherwise draw over the popup's border.

**Images (`images.rs`).** Drawing calls `want()` for photos on screen; after the frame, `fetch()` starts TDLib downloads and decode/encode on blocking threads, which report back as `ImageEvent`s. The message's embedded blurry thumbnail is shown until the real image is ready. The terminal's image protocol and cell size are queried once at startup (`main.rs`), before key reading starts. Chat photos for the list (`want_avatar`/`avatar`) are kept apart from message photos, in an LRU of `MAX_AVATARS` that survives switching chats; they download with `Tg::download_quiet` (low priority, errors not shown) and are cut by `images::circle` with transparent corners, so the selected row's highlight shows around them. A new one isn't drawn while a popup may cover the list (`ChatList.covered`): kitty sends an image only with its first drawing, and a popup drawn over that would lose it for good.

**Photo viewer (`viewer.rs`, `ui/viewer.rs`).** Enter on a photo (`Target::Photo`, from `file_target`) opens `PhotoView` over everything but the status bar: `Msg.photo`, the photo's largest size, as big as fits with its shape kept but never past its own pixels (`ui::viewer::shot`), through the same `Images::want`/`get` as bubbles, with the bubble's copy (without its blurry thumbnail) standing in until it's downloaded. `h` / `l` go to the photo before or after it among the loaded messages (`App::view_next_photo`; past those, a page of older or newer ones is loaded for the next press). `j` / `k` zoom through `viewer::SIZES`, shares of the size that fills the window and never more, so the whole photo always shows and nothing bigger than the window is encoded (a small photo opens at its own size, `PhotoView.natural`, and `j` can enlarge it up to filling the window). Each size is a new encode, so while one gets ready "Loading…" takes the picture's place in the middle, where the eyes are, and the title says "loading…" until the photo itself is drawn at the size asked for. `o` closes it and opens the file in its app as Enter used to (through `open_downloaded`, so `SAFE_TO_OPEN` still applies), and `y` copies it, both unless Telegram says it can't be saved (`viewer::cant_copy`). It closes on switching chats, logging out, and the message being deleted or edited to another photo (`PhotoView::lost`); with sixel or iTerm2 the screen is cleared when it opens, closes, zooms or goes to another photo (`App.shown_in_viewer`), since their pixels would stay. Photos shown only while open never get here: they have no `Msg.photo`.

**Voice messages (`voice.rs`, `sound.rs`).** `Msg.voice` (`Voice`: the file, the length, TDLib's waveform unpacked from 5-bit levels, `listened`) is a row of its bubble (`ui::messages::VoiceRow`): ▶ (▌▌ while it plays), the waveform as ▁–█ bars (`voice::bars`, `Voice::columns` wide by its length), its length or the time played, and a dot until you've played it; the time of day sits on the same row when there's no caption (`MetaAt::Voice`). Enter (`App::play_voice`; Enter again pauses) sets `Player.now` and asks TDLib for the file, and `TgEvent::Downloaded` starts a thread (`Player::start`) that reads the file's packets (`OggPackets`), decodes them (`OggOpus` with `opus::OpusDecoder`: RFC 7845's pre-skip, output gain and end trimming, stereo mixed down) into a `sound::Sink` a little ahead of what's heard (`Sink::wants_more`), and sends `VoiceEvent`s (`Happened`; `Heard` says when sound has started and notices a device that stalls), each with its playback's ticket so a stopped one's are dropped; `Player::on_event` hands them on as `News`. The app and the thread share a pause, a stop and the samples heard (`Shared`); `Player::playback` turns those into the bubble's progress each frame, and the run loop wakes every `TICK` while it plays (`Player::next_tick`). macOS and Windows play through cpal at the device's own rate (`Resampler`); pausing plays silence. Linux plays through ALSA's `snd_pcm_set_params`, which converts; pausing drops ALSA's buffer and resuming writes again what it hadn't played. Tests and the demo use `Output::Nowhere` (`sound::Silent`), which makes no sound.

**Notifications (`notify.rs`).** TDLib's notification API, switched on at `authorizationStateReady` (`notification_group_count_max`). It already applies mutes and drops messages read elsewhere; `App::on_notifications` also drops messages from before startup (`notify_since`) and any the user sees anyway (`App::sees`: the window has focus, or, where the terminal never reports focus, the chat is open on its newest message). `Notifier` sends at most one notification per `GAP`, everything waiting as one, and drops a chat's messages for `QUIET_CHAT` after it had one. The code is picked from the `notifications` setting (on/off with Enter or Space in the `?` popup, `App::set_notifications`) or the environment (`notify::detect`: OSC 99, 777, 9 or the bell) and wrapped for tmux passthrough. The window title counts unread unmuted chats (`updateUnreadChatCount`); it's saved at startup and put back at exit and in the panic hook.

**Sending files (`attach.rs`).** Files wait in `OpenChat.attachments` until Enter sends them, with the composer's text as the caption (`Tg::send_files`: one album per `attach::albums` group, in order, in one task so they arrive in that order). They come from `a` (a `PromptKind::Attach` prompt; Tab runs `attach::complete` and lists the matches), from `p` / Ctrl-v (`Clipboard::paste`: copied files, else an image saved as PNG, or JPEG if too big, in `outbox/` under the data directory, else text), and from pastes: dropping files on a terminal types their paths, so a paste that is only absolute paths of existing files (`attach::pasted_paths`, which reads the shell-style quoting terminals use) attaches them, and `OpenChat.dropped` lets Ctrl-z turn them back into the pasted text. `Attachment::new` decides photo or file: JPEG/PNG/WebP within Telegram's photo limits go as photos, everything else as files; Ctrl-t (`OpenChat.as_files`, reset after sending) sends the photos as files instead. The composer shows each photo's picture in a row above the names, as big as a link preview's (`ui::draw_previews`, `thumbnail_cells`), with a count of those that don't fit, and none with halfblocks: `Attachment::preview` numbers it with its own negative `image_id`, never one of TDLib's, and `Images::local_file` has it decoded from its path instead of downloaded. While a message is on its way, `updateFile` fills `OpenChat.uploads` and its bubble says "sending 45%". An edit stashes the attachments (`Editing.attachments`) and puts them back; files can't be added to an edit. Old pasted images are removed from `outbox/` at startup (`clipboard::clean_outbox`), not right after sending, since TDLib uploads from the file and resumes uploads after a restart.

**Clipboard (`clipboard.rs`).** `y` copies with arboard. Text falls back to an OSC 52 escape sequence when there's no system clipboard (e.g. over SSH). Media is downloaded through TDLib first (`App.copying`); photos are decoded on a blocking thread and come back as `Decoded` to be copied as images, other files are copied as file references. Tests never touch the real clipboard: it would overwrite whatever the user had copied.

**Demo (`demo.rs`).** `tuigram --demo` builds an `App` with made-up chats (`Chats::add_local`, `OpenChat.messages`) and draws it with `ui::draw` in a loop of its own, switching between scenes by setting `App` fields (keys 1–9, 0: reading, replying, reacting, a filtered search, a trip chat with a link preview, poll, formatting and a forward, a bot's buttons, a secret chat with countdowns and a covered photo, `:key`, and the `?` popup's two tabs; then, with Tab only, a forum's topics with one open); each scene builds its chat again, so countdowns start over. It never calls `App::run` or `on_key`, which talk to TDLib: its `Tg::detached` must make no requests. Photos are drawn procedurally, saved to a temp folder and registered with `Images::on_downloaded`, so `Images::fetch` never asks for a download. README screenshots come from it.

**Themes (`theme.rs`).** A theme is a TOML file: a 16-color `[palette]` (neutral names: `bg`, `surface`, `comment`, …, `blue`, `accent`), optional `[colors]` setting single `Colors` roles (a palette name, `#rrggbb` or `reset`), and optional `inherits`. `theme::colors` works out every role from the palette (own bubbles are `bg` tinted with `blue`, less on a light `bg`), so a palette alone is a whole theme. The built-in ones are `themes/*.toml`, embedded with `include_str!` (`BUILT_IN`); the user's are `.toml` files in `themes/` in the data directory, read by `Themes::load` at startup and again whenever `?` opens, so edits show without a restart. A user's file named like a built-in theme replaces it, and `inherits` of its own name then means the built-in one. `Settings.theme` is a theme's file name; one that's missing or broken leaves `Colors::default()` (Mocha) in use with a status message (`App::use_saved_theme`), but stays saved so fixing the file is enough. `App.colors` holds the colors in use. Drawing code uses `Colors` roles (`accent`, `own_bubble`, `search`, …), never palette names. Add a role when a new kind of thing needs a color, and to the README's table. The `?` popup lists the themes after the checkboxes, since the user's can make a long list, and scrolls (`SettingsMenu.settings_scroll`).

## Conventions

- Rust 2024 edition; `let` chains are used freely.
- Comments explain why, in plain sentences; doc comments describe behavior as the user sees it.
- Test names are sentences (`own_messages_sit_on_the_right_and_others_on_the_left`). UI tests render into a `TestBackend` buffer and assert on rows/cells.
- tdlib-rs `Message` has no `Default`, so logic that takes messages is written to accept already-converted `Msg`s where it needs testing (see `OpenChat::add_page`).
